# Change Control

A methodology change must record the objective or current condition, files and outputs affected, compatibility impact, evidence, tests, standards impact, reviewer, and approval.

Breaking changes require:

- methodology changelog entry;
- compatibility and supersession guidance;
- updated fictional example;
- semantic and mutation tests;
- exact release notes;
- deterministic package regeneration;
- controlled GitHub release and public read-back seal.

Historical tags and release assets are preserved. Corrections are published through errata and superseding releases, not silent history rewriting.
